# الأمان، التفعيل، النسخ والاستعادة

## 1. الأصول وحدود الثقة

الأصول الحساسة: ملف قاعدة البيانات/نسخه، هواتف وملاحظات العملاء والموردين، أسعار التكلفة وهوامش الربح، بيانات الموظفين، مفاتيح تشفير DB/backup، جلسات المستخدمين، ومفتاح توقيع الرخص الداخلي. واجهة React غير موثوقة أمنيًا: كل صلاحية والتحقق والحساب المالي النهائي داخل Rust.

التشفير يحمي البيانات الساكنة من قراءة القرص عند إغلاق التطبيق، لكنه لا يمنع مسؤول Windows الذي يملك جلسة المستخدم من التقاط الشاشة/الذاكرة أو تعديل ملفات البرنامج. تشفير قاعدة البيانات ليس بديلًا عن Windows account محمي، ACLs، وتحديثات Windows ومضاد الفيروسات.

## 2. قاعدة البيانات والبيانات الشخصية

- قاعدة كاملة مشفرة بـ SQLCipher. لا تنشأ قاعدة SQLite plaintext كـ fallback عند غياب SQLCipher أو خطأ المفتاح.
- أرقام العملاء والملاحظات تخزن في أعمدة ciphertext باستخدام AEAD مع nonce فريد؛ رقم الهاتف للبحث المطابق فقط يُمثّل HMAC بمفتاح lookup منفصل محفوظ تحت DPAPI. لا نحفظ نسخة الهاتف plaintext لمجرد جعل البحث أسهل.
- أسماء العملاء يمكن تشفيرها أيضًا وفق متطلبات التقارير؛ تحفظ snapshots الضرورية في الفواتير مع تقليل بيانات التعريف.
- المبالغ وبيانات المنتج ليست أسرار وصول؛ تمنع صلاحيات API أن تصل أسعار التكلفة للواجهة/الكاشير.
- لا تُسجل أرقام هاتف أو اسم عميل أو كلمات مرور أو مفاتيح أو محتوى `.req/.lic` كاملًا في سجلات الأخطاء. سجل تقني منقح يضم رمز خطأ وUUID للعملية فقط.
- موافقة العميل اختيارية ومنفصلة: `consent_status`, `consent_at`, `purpose`. من يرفض برنامج الولاء يمكنه الشراء كضيف. تحدد سياسة الاحتفاظ والحذف مع المالك/الامتثال المحلي.

## 3. إدارة مفاتيح Windows

1. ينشئ POS مفتاح DB عشوائيًا 256-bit باستخدام CSPRNG. لا يشتق المفتاح من كلمة مرور الكاشير أو serial الجهاز.
2. يحفظ **غلاف المفتاح** باستخدام `CryptProtectData` في نطاق Windows user الحالي (`CRYPTPROTECT_UI_FORBIDDEN` دون `LOCAL_MACHINE` ما لم تعتمد إدارة تشغيل مختلفة)، داخل مجلد بيانات التطبيق مع ACL مقصور على حساب تشغيل التطبيق.
3. مستخدمو POS (كاشير/مدير/مالك) يكونون حسابات التطبيق داخل Windows account مخصص/مقيد للمحل. تغيير Windows profile/إعادة تثبيت النظام قد يمنع DPAPI من فك المفتاح.
4. وجود صلاحيات مسؤول Windows قد يسمح للتلاعب بعملية التطبيق أو الوصول لمفاتيح الجلسة؛ DPAPI دفاع طبقي لا HSM للمتجر.
5. لإعادة بناء الجهاز: استعادة `.bkz` بمفتاح الاسترداد/كلمة مرور النسخة، ثم إنشاء مفتاح DB محلي جديد وتشفير DB المستعادة به. لا ننسخ ملف DPAPI blob القديم كوسيلة نقل وحيدة.
6. لا تكتب ملفات قواعد بيانات plaintext إلى `%TEMP%`. الاستعادة تتحقق في الذاكرة/ملف SQLCipher جديد مشفر، ويستخدم `SecureZeroMemory`/`zeroize` لمسح buffers حيث يمكن.

## 3.1 خزنة مفتاح التوقيع (لوحة Super Admin)

- مفتاح توقيع الرخص **لا يوجد في تطبيق العميل ولا في المستودع**: تطبيق العميل يحمل المفتاح العام فقط.
- اللوحة تحفظ البذرة (32 بايت) في `vault.bin` مشفّرة بـAES-256-GCM تحت مفتاح بيانات عشوائي. مفتاح البيانات ملفوف مرتين: بمفتاح مشتق من كلمة مرور المشغّل عبر Argon2id (64 MiB، 3 جولات) بملح عشوائي، وبـ**Windows DPAPI** (`CryptProtectData` في نطاق حساب المشغّل مع entropy خاص بالتطبيق). البذرة في الذاكرة فقط أثناء فتح الخزنة وتُمسح عند القفل.
- كلمة مرور الخزنة لا تُحفظ في أي مكان، والخزنة ملف على جهاز المطور: نسخُه احتياطيًا مسؤول المشغّل لا التطبيق.
- **الخزنة مربوطة بحساب Windows**: نسخ `vault.bin` إلى جهاز آخر أو إلى حساب آخر لا يفتح الخزنة، ولهذا التطبيق يعمل على Windows فقط ويرفض العمل على أنظمة أخرى بدل أن يفتح خزنة بلا حماية.
- **حدود معروفة**: الإلغاء لا يصل إلى جهاز عميل غير متصل (الإلغاء يُسجَّل في سجل محطة العمل فقط)، والحماية بقدر قوة كلمة المرور وحساب Windows وجهاز المشغّل، ومن قرأ ذاكرة العملية أثناء فتح الخزنة قرأ المفتاح. في الإنتاج، يُستبدل الملف بـHSM أو Windows CNG مع صلاحيات مُدقَّقة وسجل تدقيق.

## 4. كلمات المرور والجلسات والصلاحيات

- تخزين PHC Argon2id لكل حساب مع salt عشوائي؛ تبدأ الإعدادات باختبار أداء على جهاز المحل (مبدئيًا 64 MiB و3 جولات وparallelism=1، وتعدّل قبل إصدار الإنتاج). إعادة التجزئة عند تسجيل الدخول إذا أصبحت المعلمات قديمة.
- منع كلمات المرور الشائعة، حد محاولات، تأخير تصاعدي، وقفل حساب مؤقت؛ لا تكشف هل اسم المستخدم موجود.
- جلسة قصيرة، قفل تلقائي (المقترح 5 دقائق خمول، قابل للضبط)، ويتطلب الخصم اليدوي/الإرجاع الحساس إعادة مصادقة عند الحاجة.
- ثلاث صلاحيات افتراضية: `cashier`, `manager`, `owner`؛ الصلاحيات الفعلية grants دقيقة على مستوى branch. لا تعرض query أو DTO حقل التكلفة للكاشير.
- الكاشير لا يقرأ تكاليف الشراء، قيمة الربح أو تقارير الهوامش والعمولات. المدير/المالك فقط حسب grants. كل API يراجع المستخدم والفرع والصلاحية.
- تغيير الصلاحيات، خصومات يدوية، عكس فاتورة، مرتجع، جرد، وتسوية مخزون: سبب إلزامي وسجل تدقيق.

## 4.1 لوحة تحكم المالك ودخولها

- لوحة المالك تُفتح **بالضغط المطول على شعار التطبيق**، والفتح وحده لا يمنح أي صلاحية: يجب إثبات الهوية أولًا.
- إثباتان مقبولان: **بصمة الجهاز** (المصادّق المنصّة: Windows Hello على الكمبيوتر، أو بصمة/وجه الجوال عبر WebAuthn) و**كلمة مرور المالك** (المسار البديل الآمن). الاثنان ينتجان جلسة لوحة قصيرة (15 دقيقة خمول) منفصلة عن جلسات البيع.
- مراسم WebAuthn **لا يقرّرها المتصفح**: المتصفح ينفّذ المراسم، وRust يتحقق من التوقيع مقابل المفتاح العام المخزَّن وقت التسجيل، ومن `rpIdHash` ومن علَم التحقق من المستخدم (UV) ومن عمر الطلب ومن استخدام الطلب مرة واحدة. لوحة المالك تخزّن **مفاتيح عامة فقط**، فنسخة قاعدة البيانات المسروقة لا تمنح المهاجم ما يوقّع به.
- الطلبات مرتبطة بنافذة قصيرة (3 دقائق) وتُستهلك مرة واحدة، وتسجيل البصمة يتطلب جلسة لوحة قائمة.
- بعد خمس محاولات فاشلة تُقفل اللوحة عشر دقائق، في كل مسارات الفتح.
- سياسات المرتجعات والضريبة التي يغيّرها المالك من اللوحة تُكتب في `system_settings` وتُسجَّل في `audit_log` بنفس السجل الذي يسجّل تغييرات الكاشير.
- **لا تُضعف بوابة الترخيص**: فتح اللوحة نفسه يمرّ على فحص صلاحية الترخيص، والصلاحيات تبقى على مستوى الدور والفرع.

## 5. سلامة المخزون والتدقيق

- `inventory_movements` هو دفتر الحركات؛ لا تعدّل الحركة القديمة ولا تحذفها. أي تصحيح حركة عكسية جديدة مع السبب والفاعل.
- `inventory_balances` projection محدث في نفس معاملة الحركة. بعد mismatch، يعاد بناؤه من دفتر الحركات بعد إيقاف البيع/تسجيل حدث تدقيق.
- مفاتيح idempotency فريدة للبيع، الاستلام، المرتجع، والنسخ؛ ومعرّفات operation UUID تمنع تكرار الخصم بسبب إعادة إرسال IPC.
- `audit_log` append-only في طبقة البرنامج، مع hash-chain لكل حدث، triggers تمنع UPDATE/DELETE العادي، وتحقق دوري من السلسلة. هذا يكشف التعديل المعتاد لكنه **ليس immutability ضد مدير Windows/مهاجم يملك الملف والمفاتيح**؛ لا ندعي WORM.
- `foreign_keys=ON`, معاملات `IMMEDIATE`, قيود CHECK/UNIQUE، `synchronous=FULL`. استخدام immutable invoice lines/payments والحركات بدل حذفها.
- منع البيع دون مخزون افتراضيًا. خيار السماح يكون إعدادًا صريحًا مغلقًا افتراضيًا، يحتاج grant `inventory.sell_negative` وسببًا مسجلًا.

## 6. الترخيص وبصمة الجهاز

### بصمة مقتصدة ومستقرة

- التنفيذ الحالي على Windows يقرأ UUID نظام SMBIOS (Type 1) فقط، ثم يحسب SHA-256 مع domain separator. لا يُرسل MAC أو الرقم التسلسلي الخام أو بيانات العميل؛ يقتصر `.req` على digest وrequest UUID والمنتج وإصدار التطبيق والوقت.
- لا يضيف المصدر حاليًا TPM hash أو fallback إلى MAC. عدم توافر UUID صالح يوقف إنشاء الطلب بدل استخدام بصمة أضعف.
- تبديل RAM/SSD/GPU/كرت الشبكة لا يفترض تغيير البصمة. تبديل اللوحة الأم أو اختلاف SMBIOS لدى بعض OEM/VM قد يغيرها؛ يلزم اختبار الأجهزة ومسار نقل/إعادة إصدار.

### ملفات وواجهة أداة التفعيل

`apps/activation-tool` مشروع Tauri مستقل عن POS. ينشئ `.req` ويستورد `.lic`؛ لا يحتاج اتصال المتجر بالإنترنت ولا يضمّن مفتاح توقيع خاصًا. يصدر المسؤول الملف من أداة الإدارة الداخلية `tools/license-issuer`. يتحقق ActivationTool وPOS من التوقيع/المنتج/الجهاز/المدة محليًا، ثم يخزنان envelope محميًا بـ Windows DPAPI تحت `%LOCALAPPDATA%\NaseejPOS\Licensing\license.state.dpapi` ليقرأه POS تحت حساب Windows نفسه.

### صيغة الرخصة وفصل المفاتيح

- `.req` يستخدم `schema_version=1`. ملفات `.lic` الجديدة تستخدم مخططًا موقّعًا version 2، مع `plan_code`=`trial_7d` أو `annual_12m`، إضافةً إلى product وlicense/customer IDs والتواريخ وبصمة الجهاز والميزات والحدود. يقبل التحقق أيضًا ملفات v1 القديمة الموقعة التي لا تحتوي `plan_code`.
- التوقيع Ed25519 على serialization JSON ثابتة. POS وActivationTool يحملان المفتاح العام فقط، ويُحقن عامّةً عبر `NASEEJ_LICENSE_PUBLIC_KEY_HEX` أثناء البناء. عدم إعداد المفتاح يمنع قبول التراخيص؛ لا يوجد fallback مفتوح.
- أداة الإصدار وسجلها المحلي منفصلان عن مشاريع العميل. سجل الإصدار الحالي JSON محلي يتضمن معرف العميل وبصمة الجهاز ومسار ملف `.lic`؛ احمِ محطة الإصدار والسجل، ولا تضع private key أو secret في Git أو ZIP العميل.
- أداة issuer الحالية تقرأ seed خامًا من ملف كمسار تطوير/تشغيل داخلي أولي فقط. إصدار تجاري يتطلب نقل التوقيع إلى HSM أو Windows CNG مع ACL وصلاحيات وتدقيق مزدوج. لا يوجد مفتاح إنتاجي في المستودع.

### التجربة والساعة والاشتراك

- `trial-7d`: رخصة موقعة مرتبطة بالجهاز صالحة سبعة أيام كاملة من وقت UTC للإصدار. `annual-12m`: اثنا عشر شهرًا تقويميًا من وقت الإصدار. عند `now >= expires_at_utc` تعتبر الرخصة منتهية؛ لا توجد مهلة سماح في التنفيذ الحالي.
- التجربة لا تبدأ تلقائيًا داخل POS: يصدرها المسؤول أوفلاين بعد استلام `.req`، ثم يستوردها العميل عبر ActivationTool. سجل الإصدار يحذر عند وجود تجربة سابقة لنفس العميل أو الجهاز لكنه لا يمنعها؛ سياسة التكرار ما زالت تحتاج اعتمادًا.
- عند نجاح التحقق، يسجل POS آخر وقت موثوق في قاعدة البيانات المحلية، ويرفض رجوع الساعة بأكثر من خمس دقائق ما دامت حالة DB السابقة موجودة. استعادة نسخة قديمة من DB أو سيطرة مسؤول Windows قد تتجاوز ذلك؛ لا يوجد خادم وقت موثوق دائم أثناء التشغيل الأوفلاين، لذا لا يعد هذا ضمانًا مطلقًا.
- لا يوجد إلغاء لحظي عن بعد لرخصة وصلت إلى جهاز غير متصل. الإصدار الجديد/نقل الجهاز لا يمحو صلاحية الملف القديم على جهاز آخر حتى انتهائه أو وصول آلية تحقق جديدة.

### نقل/استبدال الجهاز وحفظ الرخصة

- ينشئ الجهاز الجديد `.req` ببصمته، وتصدر جهة الإدارة `.lic` جديدة مرتبطة به بعد مراجعة الاستحقاق. رخصة الجهاز القديم لا تنتقل بتغيير اسم الملف.
- يمكن حفظ نسخة `.lic` احتياطية من ActivationTool؛ احفظها في مكان آمن، فالرخصة غير مشفرة بذاتها قبل الاستيراد. DB ومفتاحها لهما مسار نسخ مستقل.

## 7. النسخ الاحتياطي `.bkz`

### التصميم

1. عند الإغلاق اليومي/الجدولة أو طلب المدير، إيقاف الكتابات القصيرة وإنشاء snapshot متسق عبر SQLCipher backup API.
2. الحزمة تشمل DB snapshot والصور المحلية وmanifest وschema version. يضغط payload بـ Zstandard قبل التشفير.
3. تشفير AES-256-GCM مع nonce عشوائي ومصادقة header؛ مفتاح data-encryption عشوائي. مفتاح النسخ اليومي محمي بـ DPAPI للتخزين المحلي، ويمكن اختيار كلمة مرور مالك للنسخ المحمولة تُشتق منها KEK عبر Argon2id (salt فريد ومعلمات محفوظة في header) لفك تغليف مفتاح البيانات.
4. لا يبقى ملف مؤقت غير مشفر. البيانات/المفتاح أثناء التجهيز في الذاكرة قدر الإمكان؛ ملفات `.part` تحمل ciphertext فقط وبـ ACL محدود، ثم `flush`/`fsync` وrename ذري إلى `.bkz`.
5. checksum/AEAD وmanifest يتحققان قبل الاستعادة. ينشأ DB جديد مشفر في مسار staging؛ يطبق migrations المطلوبة، يفحص `integrity_check`, `foreign_key_check`, المرفقات، ثم يعرض ملخصًا. لا يستبدل DB الحي قبل اكتمال كل الاختبارات.
6. قبل swap تحفظ نسخة أمان تلقائية من DB الحية. الإبدال ذري قدر الإمكان بعد إغلاق الاتصالات. إذا فشل أي فحص تبقى البيانات الحية كما هي ويعرض رمز خطأ واضح.

### سياسة تدوير مقترحة

- نسخة تلقائية واحدة يوميًا بعد إغلاق/خمول، ونسخة فورية قبل ترقية البرنامج أو الاستعادة.
- افتراضي مبدئي: آخر 14 يومية + 8 أسبوعية + 12 شهرية، قابل للتعديل. احتفظ بنسخة خارج الجهاز (USB/قرص خارجي)؛ تدوير النسخ المحلية لا يحمي من سرقة/تلف الجهاز.
- يعرض المدير آخر نجاح/فشل وحجم الملف ووجهته. لا تحتوي السجلات كلمة مرور النسخ أو مفتاحها.
- اختبار استعادة فعلي على جهاز/VM آخر كل شهر، وليس مجرد التحقق من وجود الملف.

## 8. الخصوصية وتقليل البيانات

- حقول تفضيلات المقاس/اللون اختيارية وتقتصر على خدمة المحل؛ لا تخزن بيانات طبية أو حساسة.
- إشعار ورضا منفصلان للولاء/التسويق، وإمكانية ترك الشراء بلا حساب عميل.
- لا توجد مزامنة أو تحليل سحابي افتراضي. تصدير البيانات للمالك يتطلب صلاحية وسجل تدقيق.
- تحديد مدد الاحتفاظ بالفواتير/الضرائب بحسب المحاسب والمتطلبات المحلية، وإخفاء/تشفير هوية العميل حين يسمح النظام بذلك دون كسر سجل الفاتورة.
