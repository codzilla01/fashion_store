# الاختبارات وحالة التحقق

## ما نُفّذ في جلسة 2026-10-14

- `npm run build` من `apps/pos-desktop`: **نجح** (`tsc -b` و`vite build`).
- `npm run build` من `apps/activation-tool`: **نجح** (`tsc -b` و`vite build`).
- `python -m unittest discover -s tests -v`: **8 اختبارات ناجحة**، تغطي المهاجرتين وتكرار migration 2، قصر إدارة الفروع على المالك، أعمدة idempotency، قيود SKU/الباركود، دفتر المخزون append-only وإسقاط الرصيد، rollback، وتدفق استبدال صوري مع صافي المخزون.
- `cargo fmt --check` لكل من `crates/license-format`, `tools/license-issuer`, POS Tauri وActivationTool Tauri: **نجح**.
- `cargo test --manifest-path crates/license-format/Cargo.toml`: **3 اختبارات ناجحة** تشمل توقيع Ed25519/رفض العبث، توافق رخص v1 القديمة، ورفض plan_code غير معروف.
- `cargo test --manifest-path tools/license-issuer/Cargo.toml`: **4 اختبارات ناجحة**، بينها إصدار تجربة 7 أيام واشتراك سنوي 12 شهرًا تقويميًا من طلبين، والتحقق من توقيعيهما وكتابة سجل الإصدار، واختبارات مدة الخطتين وسلامة سجل JSON.
- `cargo check` لـ `tools/license-issuer`: نجح ضمن تجميع/اختبارات الأداة.
- `cargo check` لكل من `apps/pos-desktop/src-tauri` و`apps/activation-tool/src-tauri`: **نجح** بعد إعداد ملفات `pkg-config` شكلية مؤقتة، لأن مكتبات Linux الأصلية GDK/WebKit غير موجودة. هذا فحص Rust لمصدر التطبيق، وليس linking/build أصليًا.

## ما لا يزال غير متحقق — لا تعتبر المنتج جاهزًا للإنتاج

- لم يُبنَ POS أو ActivationTool كـ Windows `.exe`/MSI، ولم يُختبر على Windows 10/11 أو WebView2/Windows SDK. لا يوجد installer موقع.
- استخدم `cargo check` ملفات `.pc` شكلية كي تتجاوز build scripts متطلبات Linux؛ لذلك لا يثبت وجود أو توافق المكتبات الأصلية ولا يثبت الربط. لم يُشغّل `cargo test` لتطبيق POS؛ الربط native غير متاح هنا.
- يلزم اختبار SQLCipher الفعلي: `cipher_version`، فتح DB بلا مفتاح، الترحيل/الإغلاق/إعادة الفتح، وفحص قاعدة الإنتاج. اختبارات Python تستخدم SQLite النظام ولا تختبر SQLCipher أو DPAPI.
- اختبارات issuer تثبت التنسيق/التوقيع والمدة محليًا بمفتاح اختبار فقط؛ لا يوجد مفتاح إنتاجي. لم يُجرَ end-to-end على Windows من `.req` إلى أداة الإدارة ثم ActivationTool ثم POS بمفتاح عام إنتاجي.
- التجربة حاليًا تصدر من أداة الإدارة الداخلية بعد استلام `.req`؛ لا تبدأ تلقائيًا داخل POS. تبدأ المدة افتراضيًا عند الإصدار، مع خيار موعد UTC مستقبلي. سياسة إعادة التجربة تحذيرية وغير مفروضة، ولا توجد مهلة سماح أو إلغاء فوري للرخص على جهاز offline.
- لم يُختبر إنشاء/استعادة النسخ المشفرة وفشل/انقطاع الطاقة أو ترحيل قاعدة حيّة على Windows. كذلك لا توجد اختبارات للطابعة/الملصقات/قارئ الباركود على موديلات المتجر.
- ما زالت سياسة المرتجعات، شمول الضريبة والتقريب، مهلة السماح بعد انتهاء الترخيص، سياسة التكرار، التسعير/التحصيل، أجهزة البيع وقناة استلام `.req` بحاجة لاعتماد واختبار كما في README وخطة التسليم.

النتائج تؤكد بناء الواجهة ومقاطع من المنطق/المخطط فقط؛ لا تُدخل بيانات متجر حقيقية ولا تبع إصدارًا تجاريًا قبل بوابات Windows وSQLCipher/DPAPI ومفتاح التوقيع واختبارات القبول والاستعادة.
